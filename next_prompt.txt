# CODEX MASTER PROMPT — CLAIMSHIELD NEXUS LIVE CLAIMS MONITORING

## MISSION: Implement Real-Time Synthetic Claims Streaming with Full Analytical Pipeline Coverage

You are working inside the **existing ClaimShield Nexus application**, developed by Team CIPHER for the Build to Care hackathon.

Your task is to implement a complete **Live Claims Monitoring Mode** on top of the existing application.

This is an enhancement of the current working system, not a new application.

### Primary objective

Add a **Start Live Simulation** button to the existing Overview dashboard.

When clicked, the system must:

1. Generate approximately one valid synthetic healthcare claim every second.
2. Persist each claim and its supporting records in PostgreSQL.
3. Run immediate applicable detection checks.
4. Schedule deeper analytical processing through the existing worker architecture.
5. Ensure every accepted claim eventually receives coverage from every applicable analytical engine.
6. Generate genuine source-linked findings when applicable.
7. Update affected investigation cases.
8. Recalculate affected SIU priorities.
9. Show actual processing events and database-backed changes in the frontend.
10. Allow the investigator to click an incoming claim, finding, or updated case and navigate to its detail page.
11. Support stopping, draining, restarting, and replaying a controlled synthetic stream.

**This must be real backend functionality. Do not simulate processing solely through frontend counters, timers, or hardcoded alerts.**

The ultimate demonstration should be:

**Start simulation → Claim arrives → Database saves it → Detection engines analyze it → Findings appear → Investigation case updates → SIU ranking changes → Frontend reflects committed results.**

The application must remain responsive throughout.

# SECTION 4 — THE REQUIRED HYBRID ARCHITECTURE

Implement two distinct analytical processing layers.

## Layer A — Immediate Processing

For each new synthetic claim:

1. Generate the synthetic claim.
2. Validate its fields and foreign-key relationships.
3. Insert the claim and applicable supporting records into PostgreSQL.
4. Record the committed ingestion event.
5. Execute applicable lightweight Claim Rules.
6. Execute applicable SupplyTrace checks.
7. Run existing-model inference if the necessary features are ready.
8. Persist source-linked detection findings.
9. Reconcile affected investigation cases.
10. Recalculate affected case priorities.
11. Publish processing results.

The target arrival rate is one claim per second.

This does not mean every analytical stage must finish within one second.

Keep ingestion and processing separate so that slow analysis does not interrupt claim generation.

## Layer B — Background Analytical Enrichment

Use the existing analytics worker or a compatible extension to process:

- Nexus Graph relationship updates
- Member Radar
- Phoenix Provider Detection
- Provider-level aggregates
- 30/60/90-day forecast inference
- Any anomaly inference dependent on refreshed aggregates
- Additional evidence fusion
- Final case reconciliation
- SIU ranking updates

Use configurable micro-batches.

A reasonable initial interval is 15–30 seconds, but the actual interval must be chosen based on measured execution time and worker availability.

### Important performance rule

Do not execute the entire historical `cli analyze` pipeline after each newly inserted claim.

Do not retrain the Isolation Forest or forecasting models after every arrival.

Where possible:

- Process only affected claims.
- Process only affected providers.
- Process only affected members.
- Refresh only changed graph neighborhoods.
- Reuse trained models.
- Reuse historical peer statistics when appropriate.
- Update only affected cases.

If an engine cannot currently process incrementally, create a safe scoped adapter or bounded batch-processing mechanism.

Do not silently omit that engine.

If full-dataset reconciliation is genuinely necessary for a particular stage, execute it through a controlled background job with explicit progress, concurrency protection, and measured cadence.

# SECTION 5 — FULL PIPELINE COVERAGE GUARANTEE

This is the most important acceptance criterion.

Every accepted streamed claim must have a traceable record of its analytical coverage.

Track at least:

- Data validation
- Database persistence
- Claim Rules
- SupplyTrace
- Isolation Forest / ML inference
- Nexus Graph enrichment
- Member Radar evaluation
- Phoenix evaluation
- 30/60/90-day forecasting coverage
- Finding persistence
- Case consolidation
- SIU priority reconciliation

For each stage, support states equivalent to:

- PENDING
- RUNNING
- COMPLETED
- NOT_APPLICABLE
- FAILED
- RETRYING

Use the project's actual naming conventions where suitable.

### Completion semantics

A claim can be marked **Fully Analyzed** only when all applicable required analysis stages have completed successfully and all required findings and case-ranking effects are committed.

Examples:

A claim without itemized supplies:

- SupplyTrace may be NOT_APPLICABLE.

A provider without an eligible Phoenix predecessor:

- Phoenix must still evaluate eligibility, then record COMPLETED with no qualifying match or NOT_APPLICABLE according to the documented contract.

A provider with insufficient history for a forecast:

- The stage must explicitly report insufficient data.
- It must not invent a valid forecast.
- Classify the result consistently as a documented terminal no-prediction outcome, not an unexplained success.

A model failure:

- Must be FAILED or RETRYING.
- Must not appear as COMPLETED or NOT_APPLICABLE.

A normal claim with no suspicious findings:

- May still be Fully Analyzed.

### Analytical dependency management

Model and relationship analyses may operate on provider or member cohorts rather than individual claims.

Therefore, link each incoming claim to its relevant background enrichment run.

Track the dataset version, snapshot boundary, or processing watermark covered by that run.

Do not mark a claim complete merely because an unrelated older analysis job finished.

When a micro-batch completes, reconcile its actual covered claim IDs or snapshot watermark before advancing stage statuses.

### Investigator-only features

Next-Best-Evidence, Groq, member confirmation, and human review are not mandatory per-claim automatic detection stages.

They are downstream investigator workflows.

Do not call Groq automatically for each claim.

Do not generate simulated member confirmations automatically for every claim.

Do not auto-resolve findings.

After new findings or queue changes, Next-Best-Evidence must read the updated state when requested.
